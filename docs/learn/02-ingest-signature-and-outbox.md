# Task 2: HMAC signature verification and the outbox pattern

## The problem

The pipeline receives payment webhooks from a fictional gateway (GatewaySim). Each webhook carries
customer data and a signature that proves it came from the gateway. Three things go wrong early in
projects like this:

1. **Replay attacks**: an attacker captures a valid webhook and re-sends it hours or days later.
   Without timestamp validation, the pipeline would process it again.
2. **Tampering**: an attacker modifies the payload (e.g., changes the amount) but keeps the old
   signature. Without constant-time HMAC verification, the pipeline might accept it.
3. **Duplicate processing**: the gateway retries on network errors, sending the same `event_id`
   twice. Without idempotency, the pipeline would create two outbox entries and downstream workers
   would process the payment twice.

Task 2 solves these three: a pure signature verification module, a Fastify endpoint that verifies
the signature before any database work, and a single transaction that writes the event and the
outbox row atomically — but only once per `event_id`.

## The decisions

- **Signature format**: `x-signature: t=<unix>,v1=<hex hmac-sha256 of "<t>.<raw body>">`. The
  timestamp `t` is seconds since epoch. The raw body is the exact bytes received (Fastify configured
  with `parseAs: 'string'` and a custom content-type parser that stores the raw body on the request
  object).
- **Constant-time compare**: `node:crypto.timingSafeEqual` prevents timing attacks on the HMAC.
- **Timestamp window**: reject signatures older than 5 minutes (`MAX_AGE_SECONDS = 300`). The
  gateway and the pipeline clocks may drift slightly; 5 minutes is generous but bounds replay risk.
- **Pure verification module**: `packages/shared/src/signature.ts` exports `verifySignature`,
  `computeSignature`, `parseSignatureHeader`, `isTimestampValid`. No I/O, no Fastify, no database —
  unit-testable without Docker.
- **Single transaction with `ON CONFLICT`**: the endpoint opens one `pg` transaction, inserts the
  event with `ON CONFLICT (event_id) DO NOTHING RETURNING event_id`, and only inserts the outbox
  row when `rowCount > 0`. A duplicate `event_id` returns 200 without a second outbox row.
- **Fast response, no broker call**: the HTTP handler returns 200 as soon as the transaction
  commits. Publishing to RabbitMQ is done by a separate outbox-relay (Task 3), not inside the
  request.
- **Env vars added**: `WEBHOOK_SECRET` (min 32 chars, generated by `gen-secrets.mjs`) and
  `INGEST_PORT` (default 3000). Both validated at startup by the shared zod config.

## Rejected alternatives

- **Verify signature inside a middleware**: would need access to the raw body before JSON parsing.
  Keeping it in the handler makes the data flow explicit and the handler testable with `app.inject`.
- **Store the parsed JSON and re-stringify for verification**: re-stringifying can change key
  order or whitespace, breaking the HMAC. The raw body must be the exact bytes received.
- **`INSERT ... ON CONFLICT DO UPDATE`**: we don't need to update the event; `DO NOTHING` with
  `RETURNING` tells us whether we inserted a new row, which is exactly the signal for the outbox
  insert.
- **Separate `SELECT` then `INSERT`**: race condition between the check and the insert. The single
  statement with `ON CONFLICT` is atomic.
- **UUID for `event_id`**: the gateway provides its own `event_id` (e.g., `evt_gateway_123`). We
  use it as the primary key to make idempotency natural — no mapping table needed.

## How it is tested

The tests came first, one per case in the task's test design:

1. `webhook_valido` — signed POST with a new `event_id` → 200, 1 row in `payment_events`, 1 row
   in `outbox`.
2. `assinatura_invalida [erro]` — POST with tampered `v1` → 401, nothing written.
3. `timestamp_velho [erro]` — `t = now - 10 min` with a correct signature → 401.
4. `evento_duplicado [borda]` — same `event_id` sent twice → 200 both times, only 1 row in `outbox`.
5. `corpo_malformado [erro]` — invalid JSON with a valid signature → 400, nothing written.

Unit tests for the signature module (`packages/shared/test/signature.test.ts`) cover:

- Valid/tampered/malformed header parsing
- Timestamp boundary (now, 4 min ago, 5 min ago, 6 min ago, future)
- HMAC determinism and collision resistance
- `verifySignature` integration (valid, tampered body, old timestamp, missing header)

Integration tests (`services/ingest-api/test/ingest.int.test.ts`) run against a real PostgreSQL
container, truncating both tables in `beforeEach`.

Run all tests:

```bash
npm run check        # typecheck + lint + unit tests
npm run test:int     # integration tests (needs docker compose up -d --wait postgres)
```

## Break it yourself

The idempotency guard is the `ON CONFLICT (event_id) DO NOTHING` clause combined with the
`rowCount > 0` check before inserting into `outbox`. Remove either one and the duplicate test
fails.

**Mutation 1: remove `ON CONFLICT`**

```sql
-- In services/ingest-api/src/app.ts (the payment_events INSERT):
-- Change:
INSERT INTO payment_events (event_id, payload) VALUES ($1, $2) ON CONFLICT (event_id) DO NOTHING RETURNING event_id
-- To:
INSERT INTO payment_events (event_id, payload) VALUES ($1, $2) RETURNING event_id
```

**Mutation 2: remove the `rowCount` check**

```ts
// In services/ingest-api/src/app.ts (the check before the outbox INSERT):
// Change:
if (eventResult.rowCount !== null && eventResult.rowCount > 0) {
  await client.query('INSERT INTO outbox ...');
}
// To:
await client.query('INSERT INTO outbox ...');
```

Run the mutation test:

```bash
# Apply one mutation, then:
npm run test:int
# Expected failure: evento_duplicado [borda] → 500 on second request (unique violation)
# or 200 both times but 2 rows in outbox (if only rowCount check removed)
```

The integration test imports `buildApp` from `src/app.ts`, so it runs the real route: you only
mutate the source, never the test. Undo with `git restore services/ingest-api/src/app.ts`.
